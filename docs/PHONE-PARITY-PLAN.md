# MOHIVX Island phone parity plan

## Goal

Bring the useful TwinDesk phone workflows into the existing MOHIVX Island desktop app and Android companion. TwinDesk is a behavior and reliability reference only; no application code is copied. Device traffic stays direct and local, with no cloud relay or external pairing service. Preserve certificate-pinned pairing, encrypted messages, per-device capabilities, and explicit Android consent.

## Stages

1. **Phone notifications and quick replies** — mirror Android notifications in the phone panel and island feed; expose only notification actions that support free-text replies. Revalidate that a notification and its reply action are still current before sending.
2. **Messages and calls**:
   - **Stage 2A (SMS conversations and sending)** — real SMS conversation thread list, opening conversations with paginated messages, and composing/sending text SMS from the PC through Android's native `Telephony.Sms` provider and `SmsManager`, gated by a separate per-device `phoneMessages` capability and explicit opt-in Android permissions (`READ_SMS`, `SEND_SMS`) without changing the default SMS app.
   - **Stage 2B (Contacts and calls)** — opt-in contact name resolution (`contacts.resolve`), call history (`calls.list`), and user-confirmed dialing via `Intent.ACTION_DIAL` (`calls.dial`), gated by independent `phoneContacts` and `phoneCalls` capabilities and explicit Android runtime permissions (`READ_CONTACTS`, `READ_CALL_LOG`) without default dialer replacement or answering/rejecting calls.
3. **Phone desk** — bidirectional file transfer and folder operations, share-sheet handoff, clipboard, and phone media controls with metadata and working previous/play/pause/next/seek. Stage 3A adds PC-to-phone file transfer; Stage 3B adds phone media session metadata and playback controls; Stage 3C adds folder creation, rename, and confirmed deletion of files or empty folders; Stage 3D adds Android share-sheet handoff (`ACTION_SEND` / `ACTION_SEND_MULTIPLE`) to the paired PC and local opt-in clipboard sync (`phoneClipboard`).
4. **Screen, apps, and multiple phones** — reliable screen control and Arabic/other keyboard layouts, remote app windows, camera/microphone routes, phone-as-display workflows, and independently placed devices.
5. **Direct transports and reliability** — local Wi-Fi plus USB/Bluetooth options where the OS exposes a supported direct link; pairing/reconnect behavior, permissions lifecycle, multi-device limits, and regression coverage.

A stage is ready for user testing only after its focused build and regression checks pass. Version and release numbering remain unchanged until an actual release is requested.

## TwinDesk pitfalls tracked for MOHIVX

- Remote keyboard language switching and non-Latin text must work; test Arabic input explicitly.
- Fast cursor movement must not trigger accidental device switching; use edge dwell and hysteresis.
- Multi-display layouts must not steal the primary display or make pointer targets overlap.
- Screen controls need an obvious, stable entry point and must report the actual sharing state.
- Phone screen/file streams must not starve low-latency control input.
- Android permissions, Play Protect, and APK signing/install behavior must be predictable; never request broad access for an unrelated feature or pretend hard-restricted permissions are granted when the installer blocks them.
- All service operations must stop or reject promptly when a phone disconnects or a capability is revoked.

## Current stage status

- **Stage 1 (implemented)**: End-to-end notification quick replies through Android notification actions that accept free text (`notifications.reply`), gated by `phoneData` and Android notification listener access.
- **Stage 2A (implemented)**: Real text SMS conversation list (`messages.threads`), conversation message history (`messages.list`), and composing/sending SMS from the PC (`messages.send`), gated by the separate `phoneMessages` desktop permission and explicit Android `READ_SMS`/`SEND_SMS` opt-in.
  - **Android permission and APK install limitation**: Android marks `READ_SMS` and `SEND_SMS` as hard-restricted permissions. When the companion APK is sideloaded/installed manually rather than through a session that allows restricted settings, Android 13+ and Play Protect / package installer policies may block granting `READ_SMS` and `SEND_SMS` unless the user explicitly enables restricted settings for the app in Android App Info (or may block them completely depending on the device/installer). Both the Android companion and PC UI report the real `messagesRead`/`messagesSend` state honestly, disable unavailable actions, and keep notification quick replies working independently.
  - **Scope boundary**: This slice is text SMS only. MMS attachments remain out of scope, and SMS stays independent of contact and call permissions.
- **Stage 2B (implemented / منفّذة)**: Opt-in contact-name resolution (`contacts.resolve` via `ContactsContract.PhoneLookup`), paginated call history (`calls.list` via `CallLog.Calls`), and user-confirmed dialing (`calls.dial` via `Intent.ACTION_DIAL`).
  - **Independent capabilities and explicit Android opt-in / صلاحيات مستقلة وموافقة صريحة في أندرويد**: `phoneContacts` (PC) + `READ_CONTACTS` (Android) gates `contacts.resolve`; `phoneCalls` (PC) + `READ_CALL_LOG` (Android) gates `calls.list`, while `phoneCalls` gates `calls.dial`. Android runtime permissions are requested only when the user explicitly taps the corresponding button in the Android Phone page. Call log queries do not read `CACHED_NAME`, so contact names are never exposed without both `phoneContacts` and `READ_CONTACTS`.
  - **Restricted `READ_CALL_LOG` limitation / قيد صلاحية `READ_CALL_LOG` المقيّدة**: Android marks `READ_CALL_LOG` as a hard-restricted permission that may be blocked for manually sideloaded APKs on Android 13+ unless restricted settings are enabled in Android App Info. When `READ_CALL_LOG` is denied (`callsRead: false`), both the Android app and PC UI report the actual permission state while keeping `ACTION_DIAL` dialer handoff available.
  - **Dialing and call control scope / حدود نطاق الاتصال والتحكم بالمكالمات**: Dialing uses `Intent.ACTION_DIAL` only so the user confirms placing the call in the Android dialer (or taps a notification when the companion is in the background). MOHIVX does not request `CALL_PHONE`, does not become the default dialer, and does not answer, reject, or end calls. SMS remains unchanged.
  - **الملخص بالعربية**: تضيف المرحلة 2B إظهار أسماء جهات الاتصال اختياريًا (`contacts.resolve`)، وسجل المكالمات (`calls.list`)، وفتح الرقم في لوحة اتصال أندرويد عبر `ACTION_DIAL` (`calls.dial`) لتأكيد المكالمة من الهاتف، بصلاحيتين مستقلتين (`phoneContacts` و`phoneCalls`) ودون استبدال تطبيق الهاتف الافتراضي أو الرد على المكالمات أو رفضها، مع إبقاء رسائل SMS دون تغيير.
- **Stage 3A (implemented; ready for user testing / منفّذة وجاهزة لتجربة المستخدم)**: PC-to-phone file uploads from the MOHIVX Files panel to the Android shared folder, in bounded authenticated chunks with progress, abort cleanup, and an independent per-device `phoneFilesWrite` permission. Android requests persistent read/write access when the user chooses a shared folder. Re-select an older read-only folder once to grant write access. The phone-to-PC download path remains available under `phoneData`.
- **Stage 3B (implemented; ready for user testing / منفّذة وجاهزة لتجربة المستخدم)**: Android reports the active media session (app, title, artist, album, playback state, duration, position, and supported actions). The PC Phone panel can issue play/pause, previous/next, and seek commands through Android's active `MediaController`. A separate per-device `phoneMedia` permission gates both metadata visibility and commands. Android notification access is required so Android can enumerate media sessions; no audio is streamed in this stage.
  - **Scope still open**: Direct phone audio to PC and actual device-level playback verification remain.
- **Stage 3C (implemented; ready for user testing / منفّذة وجاهزة لتجربة المستخدم)**: Create folders inside the selected writable Android folder, rename listed files or folders, and delete selected files or empty folders from the PC Phone panel after an explicit confirmation. Operations use the separate `phoneFilesWrite` capability, bounded names, current opaque file IDs, the Android Storage Access Framework grant or existing all-files grant, and sanitized acknowledgements. Non-empty folders are refused; the list is refreshed after successful changes.
  - **Scope still open**: Direct phone audio to PC and actual device-level folder-operation verification remain.
- **Stage 3D (implemented; ready for user testing / منفّذة وجاهزة لتجربة المستخدم)**:
  - **Android Share-sheet handoff to paired Windows PC (`ACTION_SEND` / `ACTION_SEND_MULTIPLE`)**: Android registers `.MainActivity` as a share target for `text/plain` and `*/*` (single and multiple files, up to 10 files at 1 byte–100 MB each). Incoming share intents are consumed once (`com.mohivx.SHARE_CONSUMED`); a short signature debounce handles activity recreation without suppressing a later intentional share of the same content. Each new share and transfer attempt gets a fresh ID. External `file://` URIs, internal package authorities, and executable/script extensions or MIME types (`.exe`, `.bat`, `.cmd`, `.ps1`, `.vbs`, `.js`, `.msi`, `.scr`, `.lnk`, `.reg`, `.apk`, etc.) are rejected before transfer. Shared files stream in 48 KB authenticated chunks over `/api/secure` -> `/api/phone-share` into `Downloads/MOHIVX Shared` with `.part` temporary staging, collision-safe naming, live progress, and abort/revocation cleanup.
  - **Local encrypted clipboard sync (`phoneClipboard`)**: Gated by an independent per-device `phoneClipboard` capability on the PC and an explicit `Enable clipboard sync` toggle in the Android Phone page (plus an explicit `phoneClipboardAutoSync` opt-in on the PC for automatic PC-to-phone clipboard push). Plain text up to 32,000 characters (64 KB UTF-8, no NUL bytes) is supported in English, Arabic, and other scripts. Android 13+ `ClipDescription.EXTRA_IS_SENSITIVE` items and secret patterns (private keys, API tokens, passwords) are blocked on both ends. SHA-256 hash tracking on both Android and Windows—plus updating `lastClipboardText` before writing to the Windows clipboard—prevents echo loops. Android reads clipboard only when MOHIVX is in the foreground or via explicit user action. No global mouse/keyboard hooks or monitor-edge triggers are added.
  - **الملخص بالعربية**: تضيف المرحلة 3D مشاركة النصوص والروابط والملفات من قائمة مشاركة أندرويد (`ACTION_SEND` و`ACTION_SEND_MULTIPLE`) مباشرة إلى الكمبيوتر المقترن عبر الاتصال المحلي المشفر (مع حفظ الملفات في `Downloads/MOHIVX Shared`)، ومزامنة الحافظة المحلية بصلاحية مستقلة (`phoneClipboard`) وموافقة صريحة في الطرفين، مع منع حلقات التكرار وحظر البيانات الحساسة والملفات التنفيذية.
- **Stage 4A (implemented; code/unit/build/APK verified, hardware unverified / منفّذة ومفحوصة برمجيًا، بانتظار التحقق على الأجهزة)**:
  - **Bounded ordered phone input queue (`src/components/phoneInputQueue.mjs`, `src/components/PhoneRemoteViewer.tsx`)**: Replaces the previous single-flight `sending.current` drop guard with a bounded FIFO queue (up to 32 actions) that serializes rapid taps, swipes, scroll gestures, keys, and Unicode/Arabic/emoji text in exact order without dropping intermediate events while an IPC `phone-input` request is in flight.
  - **Arabic & layout-independent keyboard handling (TwinDesk pitfall #10)**: Preserves IME composition (`onCompositionStart`/`onCompositionEnd`/`onBeforeInput`), ignores `Enter`/`Backspace`/`Escape` during active IME composition, resolves `Ctrl`/`Meta` + `A/C/X/V` shortcuts via physical key codes (`KeyA`/`KeyC`/`KeyX`/`KeyV`) as well as Arabic/Latin keys (`ش`/`ؤ`/`ء`/`ر`) while ignoring `AltGr` (`altKey: true`), and captures direct printable keystrokes when focus is on the viewer canvas. On Android (`PhoneControlService.kt`), text editing ignores `isShowingHintText` placeholder text and updates the selection cursor after `ACTION_SET_TEXT`.
  - **Anti-starvation & immediate cancellation on stop/disconnect/revocation**: `PhoneSync` reserves dedicated pending capacity for `input` commands, prioritizes `input` commands ahead of bulk data/file commands in FIFO order, and immediately rejects/clears queued inputs when screen sharing stops (`capture.stop` / `phone-media-stop`), the phone disconnects, or `phoneControl`/`phoneScreen` capabilities are revoked.
- **Stage 4B (implemented; code/unit/build verified, hardware unverified / منفّذة ومفحوصة برمجيًا، بانتظار التحقق على الأجهزة)**:
  - **Multi-monitor non-overlapping placement & shared-boundary protection (open TwinDesk issue #22)**: `src/components/phonePlacement.mjs` and `src/components/PhoneDeviceMap.tsx` preserve the Windows primary display (`screen.getPrimaryDisplay()`) read-only, resolve cards to avoid monitor/card overlap when the board has enough space (fallback may overlap if no valid position exists), and detect shared interior boundaries between adjacent Windows monitors (`isSharedMonitorBoundary`) so normal cross-monitor PC mouse travel is never hijacked.
  - **Opt-in display-edge viewer docking with velocity ceiling, dwell, and hysteresis (informed by closed TwinDesk issue #66)**: When `phoneEdgeHandoff` is explicitly enabled and a paired phone has `phoneScreen` + `phoneControl` capabilities, a fresh sync status with `controlEnabled`, and a currently live screen frame, the Electron main-process coordinator (`electron/main.cjs`, `electron/services/phoneViewer.cjs`, `createEdgeHandoffController`) samples `screen.getCursorScreenPoint()` against the placed phone's exposed outer monitor edge. Fast cursor flicks (`speed > 1.6 px/ms`) do not trigger switching; after opt-in edge dwell (within `6 px` of the outer edge for `>= 220 ms`), it opens/focuses the docked PC PhoneViewer, enables viewer interaction only when live, and does not transfer the OS cursor or globally route pointer movement. A stopped or expired screen stream releases the viewer handoff immediately.
  - **Safe release & OS boundary**: Pressing `Escape`, toggling control off, stopping screen sharing, disconnecting the phone, or revoking `phoneScreen`/`phoneControl` immediately clears the input queue, cancels pending `PhoneSync` inputs, and engages a `32 px` spatial hysteresis + `600 ms` cooldown (`phone-edge-handoff-release`) before re-arming. Because Android's unprivileged `AccessibilityService` (`PhoneControlService.kt`) dispatches touch gestures/text rather than rendering a hardware OS cursor on the physical phone glass (which would require a Bluetooth HID mouse profile or root/InputManager privilege), MOHIVX opens/focuses the docked PC `PhoneViewer` window at that display edge and enables viewer interaction only when live, without transferring the OS cursor or globally routing pointer movement, and without installing a global Windows `WH_MOUSE_LL` cursor trap.

## Remaining full-scope roadmap (Stages 4–5)

- **Stage 4 — Screen, input, audio, camera/mic, and multi-phone placement**:
  - **Screen and control validation**: test click/drag/scroll/navigation and multilingual keyboard on real phones; decide whether a safe, real desktop-cursor handoff can be supported beyond the current docked viewer interaction.
  - **Audio, camera, and microphone routing**: direct phone audio playback to PC, plus end-to-end device verification and hardening of virtual camera and virtual microphone routes.
  - **Multi-phone behavior**: verify simultaneous phones and their independently saved placements against real multi-monitor setups; edge docking currently focuses one phone viewer at a time.
- **Stage 5 — Direct local transports and long-session reliability**:
  - **USB / Bluetooth / local transports**: automatic transport selection and seamless fallback across local Wi-Fi, USB tethering / ADB-free direct USB networking, and Bluetooth PAN where supported by Windows and Android, keeping all traffic strictly local and peer-to-peer.
  - **Reliability & lifecycle hardening**: automatic reconnect after sleep/network changes, multi-device concurrency limits, permission revocation recovery, and end-to-end hardware regression testing.
